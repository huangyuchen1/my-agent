# Code Review Skill

## 审查重点

### 1. 正确性 (Correctness)
- 代码逻辑是否正确？
- 是否处理了边界情况？
- 是否有潜在的 Bug？

### 2. 安全性 (Security)
- 是否存在 SQL 注入、XSS、CSRF 风险？
- 敏感数据是否正确处理？
- 权限检查是否完整？

### 3. 性能 (Performance)
- 是否有不必要的循环或计算？
- 数据库查询是否优化？
- 是否有内存泄漏风险？

### 4. 可维护性 (Maintainability)
- 代码是否清晰易读？
- 命名是否准确表达意图？
- 是否有重复代码可以抽取？

### 5. 测试覆盖 (Test Coverage)
- 核心逻辑是否有测试？
- 边界情况是否覆盖？
- 测试是否可维护？

## 审查清单

### PR 描述检查
- [ ] 有清晰的标题和描述
- [ ] 关联了相关 Issue
- [ ] 说明了测试方法

### 代码质量
- [ ] 遵循项目代码规范
- [ ] 无硬编码配置
- [ ] 错误处理完善
- [ ] 日志记录适当

### API 设计 (如适用)
- [ ] RESTful 命名规范
- [ ] 请求/响应格式一致
- [ ] 状态码使用正确

### 数据库 (如适用)
- [ ] 迁移脚本可逆
- [ ] 索引合理
- [ ] 无 N+1 查询问题

## 反馈原则

### 建设性反馈
- **指出问题**: 具体说明哪个文件、哪行代码
- **解释原因**: 为什么这是一个问题
- **给出建议**: 如何改进

### 使用前缀区分优先级
- `nit:` - 小问题，不影响合并
- `suggestion:` - 建议，可选改进
- `question:` - 需要澄清
- `issue:` - 必须修复才能合并

### 示例
```
nit: 这个变量名 `d` 可以改为更清晰的 `data` 或具体含义

suggestion: 可以考虑用 dict.get(key, default) 简化这段逻辑

question: 为什么这里用 try-except 而不是 validate？

issue: 这个查询有 SQL 注入风险，需要使用参数化查询
```

## 审查流程

1. **理解上下文**: 查看 PR 描述和相关 Issue
2. **本地测试**: checkout 分支，运行测试
3. **逐文件审查**: 按重要性排序
4. **总结反馈**: 清晰的 approve/request-changes
